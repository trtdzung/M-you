## Data/API contract changes

Current `HomeInsightResult` returns only `{ insight, reason?, cached }`, while the underlying snapshot already contains both `healthScore` and sorted `candidates`. Extend the Home response with a typed, versioned carousel payload without adding a new parallel financial engine.

Target conceptual response (adjust naming to fit project conventions and keep backward compatibility where reasonable):

```ts
interface HomeInsightCarouselResult {
  snapshotId: string;
  asOf: string;
  healthScore: FinancialHealthScoreResult;
  healthAssessment: HealthScoreAssessment | null;
  insights: HomeInsight[]; // up to the top 2 candidates, deterministic order
  // Keep `insight` as a legacy alias for the current primary selected insight if tests/consumers need it.
  insight: HomeInsight | null;
  cached: boolean;
  reason?: "no_candidate" | "dismissed";
}

interface HealthScoreAssessment {
  snapshotId: string;
  source: "agent";
  summary: string;
  pillarAssessments: Array<{
    pillar: "SPEND" | "SAVE" | "BORROW" | "PLAN_PROTECT";
    status: "strength" | "watch" | "insufficient_data";
    explanation: string;
  }>;
  strengths: string[];
  areasToWatch: string[];
  recommendedActions: string[];
  dataLimitations: string[];
}
```

Use project-specific names and strict runtime validation. Avoid unbounded `Record<string, unknown>` where a discriminated/typed interface can be used. Validate payload length and array/string limits for agent-supplied narrative. Validate `snapshotId` and the expected pillar enum. The current validator intentionally disallows digits/URLs/code fences in the short candidate title/body; keep those safety constraints for candidate copy, but do not accidentally reject the separate structured assessment just because legitimate metric explanations refer to scores. Nevertheless, any numbers in agent prose must match facts already available in the snapshot; prefer rendering numeric values from typed metrics instead of asking the model to repeat them.

Cache requirements:
- Cache the carousel result under the existing `home_insight_cache` per `(cif, snapshot_id)`; do not create a third persistence subsystem.
- Handle old `card_json` entries safely: validate a versioned new payload, and rebuild/refresh old single-card entries rather than casting them to the new schema.
- Preserve the current agent/fallback TTL distinction if it still applies; define whether the result is fully agent-assessed or partially fallback, and don't mark a fallback narrative as agent-generated.
- Health Score must still be returned/displayable when `snapshot.candidates` is empty. The current early return `if (!snapshot.candidates.length) return { insight: null, reason: "no_candidate", cached: false }` must be revised so no candidates does not hide an available score.
- Preserve event handling (`displayed`/`dismissed`) and the existing SQLite schema unless a schema change is genuinely needed. If changing stored payload shape only, a DB migration should not be required; add tests for legacy cache parsing.
